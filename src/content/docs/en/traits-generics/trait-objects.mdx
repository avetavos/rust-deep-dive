## Static vs Dynamic Dispatch

Rust gives you two ways to use trait polymorphism:

- **Static dispatch** (via generics): the compiler knows the exact type at compile time and generates specialized code for each one. Zero runtime overhead.
- **Dynamic dispatch** (via `dyn Trait`): the concrete type is not known until runtime. The compiler stores a *vtable* — a table of function pointers — alongside the value so the right method can be found at runtime.

## The `dyn Trait` Syntax

When you write `dyn Animal`, you are asking Rust to use dynamic dispatch. Because the size of the concrete type is unknown at compile time, you must put a `dyn Trait` behind a pointer. The two most common forms are:

- `&dyn Trait` — a borrowed trait object (no heap allocation)
- `Box<dyn Trait>` — an owned trait object stored on the heap

```rust
trait Animal {
    fn sound(&self) -> &str;
    fn name(&self) -> &str;
}

fn make_sound(animal: &dyn Animal) {
    println!("{} says: {}", animal.name(), animal.sound());
}
```

This function accepts *any* type that implements `Animal` — you do not need to know the concrete type at compile time.

## Storing Mixed Types in a Collection

The most powerful use case for trait objects is storing values of different concrete types together in a `Vec` or other collection. With generics alone this is impossible — a `Vec<T>` can only hold one concrete type at a time.

```rust
trait Animal {
    fn sound(&self) -> &str;
    fn name(&self) -> &str;
}
struct Dog;
struct Cat;
impl Animal for Dog {
    fn sound(&self) -> &str { "Woof" }
    fn name(&self) -> &str { "Dog" }
}
impl Animal for Cat {
    fn sound(&self) -> &str { "Meow" }
    fn name(&self) -> &str { "Cat" }
}

let animals: Vec<Box<dyn Animal>> = vec![
    Box::new(Dog),
    Box::new(Cat),
    Box::new(Dog),
];
```

Each element is a `Box<dyn Animal>` — an owned pointer to some type that implements `Animal`. The vtable stored alongside each value ensures the right `sound()` and `name()` implementations are called.

## `impl Trait` vs `dyn Trait`

Both `&impl Animal` and `&dyn Animal` accept "some type that implements `Animal`" as a function parameter, but they compile very differently:

```rust
trait Animal {
    fn sound(&self) -> &str;
}
struct Dog;
impl Animal for Dog { fn sound(&self) -> &str { "Woof" } }

// Static dispatch -- compiler generates specialized code per concrete type
fn notify_static(item: &impl Animal) {
    println!("{}", item.sound());
}

// Dynamic dispatch -- resolved at runtime via vtable
fn notify_dyn(item: &dyn Animal) {
    println!("{}", item.sound());
}

fn main() {
    notify_static(&Dog);
    notify_dyn(&Dog);
}
```

`&impl Animal` is shorthand for a generic type parameter (`fn notify_static<T: Animal>(item: &T)`) — the compiler monomorphizes it, just like the generics you saw in the previous lesson. `&dyn Animal` is a trait object — one function, dispatched through a vtable at runtime. Use `impl Trait` when you know the type at compile time and want maximum performance; use `dyn Trait` when you need runtime flexibility, such as storing mixed types in a `Vec` or returning different types from different branches.

## Trait Objects and Dyn Compatibility

Not every trait can be used as a `dyn Trait`. A trait is **dyn compatible** if, roughly:

1. It has no methods that return `Self`.
2. It has no generic type parameters on its methods.

(Older material — including some of Rust's own history — calls this *object safety*; current rustc uses the term *dyn compatible* / *dyn compatibility* in its diagnostics, so that's what this lesson uses.)

The standard library traits `Display`, `Debug`, and `Iterator` are dyn compatible. Traits like `Clone` (whose `clone` method returns `Self`) are not — trying to use one as `&dyn Trait` is a compile error:

```rust
// @expect-error E0038
trait Animal {
    fn sound(&self) -> &str;
    fn clone_animal(&self) -> Self; // returns Self -- not dyn compatible
}

struct Dog;

impl Animal for Dog {
    fn sound(&self) -> &str { "Woof" }
    fn clone_animal(&self) -> Self { Dog }
}

fn make_sound(animal: &dyn Animal) {
    println!("{}", animal.sound());
}

fn main() {
    make_sound(&Dog);
}
```

### The `where Self: Sized` Escape Hatch

You don't have to give up on the whole trait just because one method is not dyn compatible. Adding a `where Self: Sized` bound to that one method removes it from the vtable requirement — the method is simply unavailable through `dyn Trait`, but the trait itself becomes dyn compatible again, and the method still works when called on a concrete, statically-known type:

```rust
trait Animal {
    fn sound(&self) -> &str;
    fn clone_animal(&self) -> Self
    where
        Self: Sized; // excluded from the vtable -- only callable when Self is statically known
}

struct Dog;

impl Animal for Dog {
    fn sound(&self) -> &str { "Woof" }
    fn clone_animal(&self) -> Self { Dog }
}

fn make_sound(animal: &dyn Animal) {
    println!("{}", animal.sound());
}

fn main() {
    make_sound(&Dog);            // fine: dyn dispatch only needs sound()
    let d2 = Dog.clone_animal(); // fine: called on the concrete type, not through dyn
    make_sound(&d2);
}
```

## When to Use Each

| Approach | Type known at compile time? | Runtime cost | Heterogeneous collection? |
|---|---|---|---|
| Generic (`impl Trait` or `T: Trait`) | Yes | Zero | No |
| Trait object (`dyn Trait`) | No | Small vtable indirection | Yes |

Use generics when you know the types at compile time and want maximum performance. Use trait objects when you need to work with a collection of mixed concrete types or when the type is determined by user input or configuration at runtime.

<Callout title="Trait objects enable runtime polymorphism via a vtable">
When you use `dyn Trait`, Rust stores a fat pointer: a pointer to the data and a pointer to a vtable (a table of function pointers for that type's trait implementation). This enables different concrete types to be stored together in collections. The cost is a small indirection per method call — usually negligible, but worth knowing about.
