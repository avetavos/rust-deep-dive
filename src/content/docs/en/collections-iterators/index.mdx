## What This Module Covers

Rust ships with a powerful set of standard-library collections and a lazy, zero-cost iterator system. Together they let you store, transform, and consume data without manual loops or unnecessary allocations.

This module walks through five focused lessons:

| Lesson | Topic |
|--------|-------|
| `Vec<T>` & `String` | Growable sequences and owned text |
| `HashMap<K, V>` | Key-value lookup with the entry API |
| Iterators | Lazy chains: `map`, `filter`, `collect`, `fold` |
| Closures | Capturing environments; `Fn` / `FnMut` / `FnOnce` |

## The Four Core Collections

Rust's most-used collections and when to reach for each:

- **`Vec<T>`** — ordered, contiguous heap array. Use when you need indexed access or a growable list.
- **`String`** — owned, UTF-8 text. Use when you need to build or mutate text at runtime.
- **`HashMap<K, V>`** — hash table mapping keys to values. Use for fast lookup by key.
- **`HashSet<T>`** — set of unique values. Use when membership testing is all you need.

## The Iterator System

Every Rust collection exposes an iterator. Iterators are **lazy** — no work happens until a *consumer* (like `collect`, `sum`, or `for`) pulls values through the chain.

```rust
let v = vec![1, 2, 3, 4, 5];

// Nothing executes yet — adaptor chain is just a description
let chain = v.iter().filter(|&&x| x % 2 == 0).map(|&x| x * 10);

// Consumer drives the chain
let result: Vec<i32> = chain.collect();
```

export const collectionsOverviewCode = `use std::collections::HashMap;
use std::collections::HashSet;

fn main() {
    // Vec<i32>
    let mut v: Vec<i32> = vec![1, 2, 3];
    v.push(4);
    println!("Vec: {:?}", v);

    // String
    let mut s = String::from("Hello");
    s.push_str(", Rust!");
    println!("String: {}", s);

    // HashMap<&str, i32> — sort keys for deterministic output
    let mut map = HashMap::new();
    map.insert("one", 1);
    map.insert("two", 2);
    map.insert("three", 3);
    let mut keys: Vec<&str> = map.keys().cloned().collect();
    keys.sort();
    for k in &keys {
        println!("{}: {}", k, map[k]);
    }

    // HashSet<i32>
    let set: HashSet<i32> = vec![1, 2, 3, 2, 1].into_iter().collect();
    let mut items: Vec<i32> = set.into_iter().collect();
    items.sort();
    println!("Set: {:?}", items);
}`;

<Callout title="Collections live on the heap; iterators are free">
All standard collections allocate on the heap and manage their own memory. Iterator adaptors like `map` and `filter` compile down to the same machine code as hand-written loops — there is no runtime overhead for chaining them.
</Callout>

## What the Compiler Says: Collections Don't Coerce Between Number Types

A collection is generic over exactly one element type — `Vec<i32>` holds `i32` and nothing else, not even a type that "should" convert. Rust never inserts an implicit numeric conversion for you, in a collection or anywhere else:

```rust
// @expect-error E0308
fn main() {
    let mut v: Vec<i32> = vec![1, 2, 3];
    v.push(3.0);
    println!("{:?}", v);
}
```

```text
error[E0308]: mismatched types
    --> src/main.rs:3:12
     |
   3 |     v.push(3.0);
     |       ---- ^^^ expected `i32`, found floating-point number
     |       |
     |       arguments to this method are incorrect

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0308`.
```

The fix is always explicit: pick the type you meant (`v.push(3)` for an `i32`, or declare `Vec<f64>` if the whole collection should hold floats) and convert at the boundary with `as` or `From`/`Into`, never by hoping the compiler will guess. The four lessons that follow show far more specific versions of this idea — a `HashMap` key that can't be a `float`, a `sum()` call the compiler can't type on its own — this is the general shape all of them share: Rust asks *you* to make the type explicit rather than silently picking one.

## Choosing a Collection

<Mermaid code={`flowchart TD

This decision tree is a starting point, not a law: `BTreeMap` is also the right call whenever you need a `Vec`-like "give me a range of keys" query that `HashMap` cannot do at all, regardless of speed.

## Mental Model

Think of every collection as **ownership plus a shape**: `Vec<T>` owns a contiguous run of `T`, `String` owns a contiguous run of UTF-8 bytes, `HashMap<K, V>` owns a hash table of `K`-to-`V` pairs. The iterator system is a *second*, orthogonal idea layered on top: it is a uniform way to walk any of those shapes one element at a time, lazily, without the walking code needing to know which shape it is walking. Once you see collections and iterators as two separate concerns — "how is the data stored" and "how do I process it" — the rest of this module is mostly variations on those two questions.

## Trade-offs

`Vec<T>` gives you cache-friendly contiguous storage and O(1) indexed access, at the cost of O(n) insertion/removal in the middle. `HashMap<K, V>` gives O(1) average lookup by key, at the cost of no ordering guarantee and a randomized-seed overhead per map. `BTreeMap<K, V>` gives you sorted iteration and range queries, at the cost of O(log n) operations instead of `HashMap`'s O(1) average. None of these is strictly better — the right choice depends on which operation ("iterate in order", "look up by key", "index by position") your code actually performs most often.

## Common Misconceptions

- **"Rust collections auto-convert element types for convenience, like some dynamically-typed languages do."** They never do — a `Vec<i32>` accepts only `i32`, full stop; every conversion is a call you write yourself.
- **"Iterators are just a nicer syntax for `for` loops, with no functional difference."** They compile to the same code as a hand-written loop, but they are also *values* — you can build a chain, pass it around, and only decide later (with `collect`, `sum`, or a `for` loop) how to consume it. A `for` loop is one specific consumer among several.
- **"`HashSet<T>` is just a `HashMap<T, ()>` you don't need to think about further."** True as an implementation detail, but it still requires `T: Eq + Hash`, the exact same requirement that trips people up on `HashMap` keys — the `hashmap` lesson covers this in depth.

## Reading AI-generated Code

AI assistants frequently reach for the "widest" ownership a function could accept — `Vec<String>` — even when the function only ever reads the data, never grows or mutates it. That forces every caller to either move an owned `Vec<String>` in or pay for a full clone just to satisfy the signature.

<SpotTheBug code={`fn print_report(lines: Vec<String>) {
    for line in &lines {
        println!("{}", line);
    }
}
`}>
`print_report` never pushes to `lines`, never removes from it, never needs to own it — it only iterates by reference. Taking `Vec<String>` by value forces every caller to give up ownership (or `.clone()` an entire `Vec<String>` just to keep their own copy). The fix borrows instead: `fn print_report(lines: &[String])` (or `&[&str]` if callers already have string slices) accepts a borrowed view without requiring ownership at all, and still works with `&some_vec` at every call site.
</SpotTheBug>

<Callout title="The one-line takeaway">
A collection is "ownership plus a shape" and an iterator is a lazy, uniform way to walk any of those shapes — pick the shape by which operation (index, key lookup, sorted range) your code does most, and never assume the compiler will convert an element type for you.
</Callout>
