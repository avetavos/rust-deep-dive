## Spawning Threads with `std::thread`

Rust's standard library provides OS threads through `std::thread::spawn`. You pass a closure, and the function returns a `JoinHandle<T>` — a handle you can use to wait for the thread to finish and retrieve its return value.

```rust
use std::thread;

fn main() {
    let handle = thread::spawn(|| {
        // This runs on a new OS thread
        42
    });

    let result = handle.join().unwrap(); // block until the thread finishes
    println!("Thread returned: {}", result);
}
```

The closure is `move || { ... }` when it needs to capture variables from the enclosing scope — otherwise the compiler cannot guarantee the captured data lives long enough.

### Moving Data Into a Thread

Because a thread may outlive the scope where it was spawned, any data the thread captures must be owned by the thread. The `move` keyword transfers ownership of captured variables into the closure.

```rust
use std::thread;

fn main() {
    let message = String::from("hello from the main thread");

    let handle = thread::spawn(move || {
        // message is moved here — the thread now owns it
        println!("{}", message);
    });

    handle.join().unwrap();
    // println!("{}", message); // would not compile — moved above
}
```

### What Happens Without `move`

Drop the `move` keyword and the closure tries to *borrow* `message` instead of owning it. The compiler rejects this: it cannot prove the borrow stays valid for as long as the spawned thread might run.

```rust
// @expect-error E0373
use std::thread;

fn main() {
    let message = String::from("hello");
    let handle = thread::spawn(|| {
        println!("{}", message);
    });
    handle.join().unwrap();
}
```

### Sharing State with `Arc<Mutex<T>>`

To share mutable data between multiple threads, wrap it in `Arc<Mutex<T>>`:

- `Mutex<T>` provides mutual exclusion — only one thread can lock it at a time.
- `Arc<T>` (Atomically Reference Counted) allows multiple threads to hold a reference-counted pointer to the same allocation.

You clone the `Arc` before moving it into each thread. The underlying `Mutex` is shared, not cloned.

```rust
use std::thread;
use std::sync::{Arc, Mutex};

fn main() {
    let counter = Arc::new(Mutex::new(0_i32));
    let mut handles = Vec::new();

    for _ in 0..4 {
        let counter = Arc::clone(&counter); // cheap ref-count increment
        let h = thread::spawn(move || {
            let mut n = counter.lock().unwrap(); // acquire lock
            *n += 1;
        }); // lock released when n drops
        handles.push(h);
    }

    for h in handles {
        h.join().unwrap();
    }

    println!("Final count: {}", *counter.lock().unwrap());
}
```

### `if let` and Lock Guards (Rust 2024)

A lock guard is a temporary value, and the 2024 edition changed when temporaries in an `if let` condition are dropped. On Rust 2021 the read guard below stays alive through the `else` branch, so asking for the write lock there deadlocks — the thread waits for a lock it is still holding itself. On Rust 2024 the guard is dropped before `else` runs:

It prints `initialized`, then `already set to true`. Compiled on `edition = "2021"` the same program hangs on the first call. If you ever want the old scoping back, write the condition as a `match` — `match` still holds its temporaries for the whole expression.

### Collecting Results from Multiple Threads

A common pattern is to have each thread compute a value and push it into a shared `Vec`. After all threads complete, you sort the results so the output is deterministic regardless of scheduling order.

export const threadsCode = `use std::thread;
use std::sync::{Arc, Mutex};

fn main() {
    let results = Arc::new(Mutex::new(Vec::new()));
    let mut handles = Vec::new();

    for i in 0..5 {
        let results = Arc::clone(&results);
        let handle = thread::spawn(move || {
            let square = i * i;
            let mut v = results.lock().unwrap();
            v.push(square);
        });
        handles.push(handle);
    }

    for h in handles {
        h.join().unwrap();
    }

    let mut final_results = results.lock().unwrap().clone();
    final_results.sort();
    println!("Squares: {:?}", final_results);
    let sum: i32 = final_results.iter().sum();
    println!("Sum: {}", sum);
}`;

### `Rc<T>` Is Not `Send`

`Arc<Mutex<T>>` works across threads because `Arc`'s reference count is atomic. `Rc<T>`'s count is a plain, non-atomic integer — two threads incrementing it at once would race. The compiler catches this at the type level, before any code runs:

```rust
// @expect-error E0277
use std::rc::Rc;
use std::thread;

fn main() {
    let data = Rc::new(42);
    let handle = thread::spawn(move || {
        println!("{}", data);
    });
    handle.join().unwrap();
}
```

```text
error[E0277]: `Rc<i32>` cannot be sent between threads safely
   --> src/main.rs:6:32
    |
  6 |       let handle = thread::spawn(move || {
    |                    ------------- ^------
    |                    |             |
    |  __________________|_____________within this `{closure@src/main.rs:6:32: 6:39}`
    | |                  |
    | |                  required by a bound introduced by this call
  7 | |         println!("{}", data);
  8 | |     });
    | |_____^ `Rc<i32>` cannot be sent between threads safely
    |
    = help: within `{closure@src/main.rs:6:32: 6:39}`, the trait `Send` is not implemented for `Rc<i32>`
```

Swapping `Rc::new` for `Arc::new` fixes it — `Arc<i32>` is `Send`, so the closure captures a type that is safe to move across the thread boundary.

<Callout title="Send and Sync make data races a compile error">
Rust's type system enforces thread safety through the `Send` and `Sync` marker traits. `Arc<Mutex<T>>` is `Send` (you can move it to another thread) and `Sync` (you can share a reference to it across threads). If you try to share a `Rc<T>` or `RefCell<T>` across threads, the compiler rejects the code with a clear error — no sanitizers needed, no runtime panics from data races.
</Callout>
