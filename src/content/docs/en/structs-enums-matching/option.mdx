## No Null in Rust

Many languages allow any variable to hold a "null" or "nil" value, leading to null-pointer exceptions at runtime. Rust takes a different approach: **there is no null**. When a value might be absent, you use `Option<T>` from the standard library.

`Option<T>` is an enum defined as:

```rust
enum Option<T> {
    Some(T),
    None,
}
```

`Some(value)` wraps a present value of type `T`. `None` represents the absence of a value. The compiler forces you to handle both cases before you can use the inner value — null-pointer bugs become compile-time errors.

Because `Option<T>` is so common, `Some` and `None` are in scope everywhere without needing `Option::` prefix.

## Handling `Option<T>` with `match`

The most explicit way to handle an `Option<T>` is a `match` expression:

```rust
fn divide(a: f64, b: f64) -> Option<f64> {
    if b == 0.0 { None } else { Some(a / b) }
}

match divide(10.0, 2.0) {
    Some(result) => println!("Result: {}", result),
    None         => println!("Cannot divide by zero"),
}
```

The compiler rejects code that only handles `Some` without `None` — the match must be exhaustive.

## `if let` for the Happy Path

When you only care about the `Some` case, `if let` is cleaner:

```rust
fn divide(a: f64, b: f64) -> Option<f64> {
    if b == 0.0 { None } else { Some(a / b) }
}

if let Some(value) = divide(10.0, 2.0) {
    println!("Got: {}", value);
}
```

The body executes only when the value is `Some`. Add `else` to handle `None` if needed.

## Let Chains — `if let` Plus Conditions (Rust 2024)

Reaching into a nested `Option` used to mean nesting `if let` blocks, because `if let` could not be combined with `&&`. The Rust 2024 edition allows **let chains**: `let` bindings and boolean tests joined with `&&` inside one condition.

<Playground code={letChainCode} />

Every `let` in the chain binds for the rest of the chain and for the body, so `user` is in scope for the second `let` and `age` is in scope for the comparison. An `else` branch still works — it runs when any link in the chain fails.

This one is edition-gated. The same code on `edition = "2021"` is rejected with `error: let chains are only allowed in Rust 2024 or later`.

## `let else` — Bind or Bail, in One Line

`let else` binds the `Some` case directly and requires its `else` branch to **diverge** (`return`, `break`, `continue`, or `panic!`), so everything after the `let` can treat the binding as unconditional — no nested `if let` block, no separate `else` scope to manage:

```rust
fn first_word(s: &str) -> Option<&str> {
    s.split_whitespace().next()
}

fn shout_first_word(s: &str) {
    let Some(word) = first_word(s) else {
        println!("nothing to shout");
        return;
    };
    println!("{}!", word.to_uppercase());
}

fn main() {
    shout_first_word("hello world");
    shout_first_word("   ");
}
```

```text
HELLO!
nothing to shout
```

## `matches!` — a Boolean Test Without Destructuring

`matches!(value, pattern)` checks whether a value matches a pattern and returns `true`/`false`, without binding anything. It is the right tool when you only need a yes/no answer to "is this `Some`? is this in range?":

```rust
fn main() {
    let maybe: Option<i32> = Some(7);
    println!("is some: {}", matches!(maybe, Some(_)));
    println!("is some and positive: {}", matches!(maybe, Some(n) if n > 0));

    let none: Option<i32> = None;
    println!("none is some: {}", matches!(none, Some(_)));
}
```

```text
is some: true
is some and positive: true
none is some: false
```

`matches!` desugars to exactly the `match value { pattern => true, _ => false }` you would otherwise write by hand — it exists purely to remove that boilerplate for the common "just tell me yes or no" case.

## `unwrap_or` — Providing a Default

`unwrap_or(default)` returns the inner value if `Some`, or the given default if `None`:

```rust
let maybe: Option<i32> = None;
let value = maybe.unwrap_or(0); // 0
```

This is the safest form of "just give me a value or a fallback." Avoid plain `.unwrap()` in production code — it panics on `None`.

<Callout title="unwrap_or vs unwrap_or_else">
`unwrap_or(default)` always evaluates `default` — even when the `Option` is `Some` and the fallback is never used. `unwrap_or(expensive_computation())` pays that cost on every call, `Some` or not. `unwrap_or_else(|| expensive_computation())` takes a closure instead, so the fallback is computed **only** when it's actually needed. Prefer `unwrap_or` only for cheap, already-computed values (`0`, `""`, a clone of something small); reach for `unwrap_or_else` the moment the fallback involves a function call, allocation, or anything non-trivial.
</Callout>

## `map` — Transforming the Inner Value

`map` applies a closure to the `Some` value and returns a new `Option<T>`. If the original is `None`, it passes `None` through unchanged:

```rust
let doubled = Some(5).map(|x| x * 2); // Some(10)
let nothing: Option<i32> = None;
let still_none = nothing.map(|x| x * 2); // None
```

`map` is essential for chaining transformations without unwrapping intermediate `Option<T>` values.

<Callout title="Rust has no null">
`Option<T>` makes the possibility of absence explicit in the type system. A value of type `i32` is always a valid integer — it can never be null. Only a value of type `Option<i32>` might be absent. This forces every caller to acknowledge and handle the absence case, eliminating an entire class of runtime crashes.
</Callout>

## The Full Combinator Tour

Beyond `map` and `unwrap_or`, `Option<T>` has a family of combinators for chaining fallible logic without ever calling `.unwrap()`:

```rust
fn first_word(s: &str) -> Option<&str> {
    s.split_whitespace().next()
}

fn parse_first_word_len(s: &str) -> Option<usize> {
    let word = first_word(s)?; // ? on Option: return None early
    Some(word.len())
}

fn main() {
    // and_then: chain another Option-returning step (like flatMap)
    let nested: Option<i32> = Some(4).and_then(|n| if n > 0 { Some(n * n) } else { None });
    println!("and_then: {:?}", nested);

    // ok_or: Option -> Result, supplying an error for None
    let maybe_id: Option<u32> = None;
    let result: Result<u32, &str> = maybe_id.ok_or("missing id");
    println!("ok_or: {:?}", result);

    // ? on Option: propagate None early, same shape as ? on Result
    println!("? on Option: {:?}", parse_first_word_len("hello world"));
    println!("? on Option: {:?}", parse_first_word_len(""));

    // as_ref: Option<T> -> Option<&T> without consuming the original
    let owned: Option<String> = Some(String::from("hi"));
    let len = owned.as_ref().map(|s| s.len());
    println!("as_ref: {:?}, owned still usable: {:?}", len, owned);

    // as_deref: Option<String> -> Option<&str>
    let maybe_string: Option<String> = Some(String::from("deref me"));
    let as_str: Option<&str> = maybe_string.as_deref();
    println!("as_deref: {:?}", as_str);

    // take: move the value out of the Option, leaving None behind
    let mut slot: Option<i32> = Some(10);
    let taken = slot.take();
    println!("take: taken={:?} slot={:?}", taken, slot);

    // zip: combine two Options into Option<(A, B)>, None if either is None
    let a: Option<i32> = Some(1);
    let b: Option<&str> = Some("one");
    println!("zip: {:?}", a.zip(b));
    let c: Option<i32> = None;
    println!("zip with None: {:?}", a.zip(c));
}
```

```text
and_then: Some(16)
ok_or: Err("missing id")
? on Option: Some(5)
? on Option: None
as_ref: Some(2), owned still usable: Some("hi")
as_deref: Some("deref me")
take: taken=Some(10) slot=None
zip: Some((1, "one"))
zip with None: None
```

`and_then` is to `Option` what `flat_map` is to iterators: the closure itself returns an `Option`, so `and_then` avoids the `Option<Option<T>>` you'd get from `map` with an `Option`-returning closure. `as_ref`/`as_deref` matter specifically because plain `map` on an owned `Option<String>` would **consume** it; borrowing first lets you inspect the inner value while keeping the original `Option` usable afterward. `take()` is the standard way to move a value out of a `struct` field that holds an `Option<T>` — it leaves `None` behind instead of requiring the whole struct to be temporarily invalid.

### What the Compiler Says: `?` Only Works Inside a Matching Return Type

The `?` operator on `Option` only compiles inside a function that itself returns `Option` (or another type implementing the same short-circuit mechanism):

```rust
// @expect-error E0277
fn first_word(s: &str) -> Option<&str> {
    s.split_whitespace().next()
}

fn bad(s: &str) -> usize {
    let word = first_word(s)?;
    word.len()
}

fn main() {
    println!("{}", bad("hi"));
}
```

```text
error[E0277]: the `?` operator can only be used in a function that returns `Result` or `Option` (or another type that implements `FromResidual`)
 --> src/main.rs:7:29
  |
6 | fn bad(s: &str) -> usize {
  | ------------------------ this function should return `Result` or `Option` to accept `?`
7 |     let word = first_word(s)?;
  |                             ^ cannot use the `?` operator in a function that returns `usize`

error: aborting due to 1 previous error
```

`?` is not "unwrap or return a default" — it always propagates through the *same kind* of wrapper the function returns. A function returning a plain `usize` has no `None` case to return into, so the compiler rejects it outright rather than guessing what you meant.

## Mental Model

`Option<T>` turns "might not be here" into a value you must open before you can use — every combinator (`map`, `and_then`, `unwrap_or_else`, `?`) is a different way of opening it, chosen by what you want to happen on `None`. There is no way to accidentally use the inner `T` without going through one of these, which is the entire mechanism that makes null-pointer-style bugs impossible: the compiler will not let you forget the `None` branch exists.

## Trade-offs

`match` is the most explicit form and reads correctly to anyone regardless of how many combinator names they know, at the cost of vertical space for a long chain of fallible steps. Combinators compress that chain into one expression, but each one (`and_then`, `ok_or_else`, `zip`) is a piece of vocabulary the reader needs before the line makes sense. `let else` sits in between — as readable as `match` for "bind or bail," but only usable when the failure path can genuinely diverge, which rules it out the moment you need a *value* on failure instead of an early return. `matches!` is the cheapest option when you truly only need a boolean, but the moment you also need the inner value, you're back to `if let`/`match`.

## Common Misconceptions

- **"`is_some()` followed by `unwrap()` cannot panic, so it's just as safe as `if let`."** True that it cannot panic in that exact shape, but it checks the variant twice (once via `is_some()`, once inside `unwrap()`), and unlike `if let Some(x) = opt`, it gives you no compiler-enforced place to handle `None` — a reviewer has to notice the missing `else` themselves.
- **"`unwrap_or(x)` and `unwrap_or_else(|| x)` always do the same thing."** They do, *if* `x` is a plain, already-computed value. The moment `x` is a function call or an allocation, `unwrap_or` pays that cost on every invocation — `Some` or `None` — while `unwrap_or_else`'s closure only runs on `None`.
- **"`?` on an `Option` unwraps it, or panics like `.unwrap()` does on failure."** It never panics. On `None` it returns `None` immediately from the *enclosing function* — which is why it only compiles inside a function whose own return type is `Option` (or `Result`, for `?` on a `Result`).

## Reading AI-generated code

AI assistants frequently write `if x.is_some() { x.unwrap() }` because it "obviously" cannot panic — but it does manually, and worse, what a single pattern match already does atomically and idiomatically, with an `else` branch reminding the reader that `None` needs handling too.

<SpotTheBug code={`fn print_balance(account: Option<i32>) {
    if account.is_some() {
        println!("balance: {}", account.unwrap());
    }
}
`}>
This compiles and never panics, but it is strictly worse than the idiomatic version: there is no branch handling `None` at all (a caller passing `None` gets total silence, not even a log line), and the variant is checked twice — once via `is_some()`, once implicitly inside `unwrap()`. The fix is `if let Some(balance) = account { println!("balance: {}", balance); } else { println!("balance unavailable"); }` — or, better, changing the function to return the formatted `String`/`Option<String>` so the *caller* decides what "unavailable" should look like, instead of the message being buried inside `print_balance`.
</SpotTheBug>

<Callout title="The one-line takeaway">
Never re-derive an `Option`'s variant with `.is_some()`/`.is_none()` before extracting the value — pattern-match, `let else`, or chain combinators so the compiler proves the extraction is safe in the same step that checks it, and reach for `unwrap_or_else` instead of `unwrap_or` the moment the fallback costs more than a literal.
</Callout>
