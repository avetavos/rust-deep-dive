## ทำไมต้องมี Error ที่กำหนดเอง?

การใช้ `String` หรือ `Box<dyn std::error::Error>` เป็น error type ของคุณนั้นใช้ได้ดีสำหรับสคริปต์เร็วๆ แต่ library และ application จริงจะได้ประโยชน์จาก error enum ที่เป็นรูปธรรม:

- ผู้เรียกสามารถ pattern-match กับ variant เฉพาะเจาะจงและจัดการแต่ละกรณีต่างกันได้
- error type บันทึกทุกโหมดความล้มเหลวของ API ของคุณไว้เป็นเอกสาร
- คุณสามารถแนบข้อมูลที่มีโครงสร้าง (เช่น ค่าที่ไม่ถูกต้อง) ไว้กับแต่ละ variant ได้

## กำหนด Error Enum

ประกาศ enum ที่มีหนึ่ง variant ต่อหนึ่งโหมดความล้มเหลว Derive `Debug` เพื่อให้ error พิมพ์ด้วย `{:?}` ได้:

```rust
#[derive(Debug)]
enum AppError {
    ParseError(std::num::ParseIntError),
    NegativeNumber(i32),
    TooBig(i32),
}
```

## Implement `Display`

trait `std::fmt::Display` ควบคุมข้อความ error ที่มนุษย์อ่านได้ — สิ่งที่คุณเห็นเมื่อพิมพ์ด้วย `{}`:

```rust
use std::fmt;

#[derive(Debug)]
enum AppError {
    ParseError(std::num::ParseIntError),
    NegativeNumber(i32),
    TooBig(i32),
}

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            AppError::ParseError(e)     => write!(f, "parse error: {}", e),
            AppError::NegativeNumber(n) => write!(f, "number is negative: {}", n),
            AppError::TooBig(n)         => write!(f, "number is too big: {} (max 100)", n),
        }
    }
}
```

## คอมไพเลอร์พูดว่าอะไร: `Error` ต้องการ `Display`

`std::error::Error` ถูกประกาศเป็น `pub trait Error: Debug + Display` หมายความว่า `Display` ไม่ใช่ตัวเลือก — มันคือ **supertrait bound** การ implement `Error` ก่อน `Display` จะล้มเหลวด้วยข้อความที่บอกชื่อ bound ที่ขาดหายไปเป๊ะๆ และที่มาของมัน:

```rust
// @expect-error E0277
#[derive(Debug)]
struct AppError;

impl std::error::Error for AppError {}

fn main() {
    let _e: Box<dyn std::error::Error> = Box::new(AppError);
}
```

นี่คือเหตุผลที่ custom error type ทุกตัวเดินตามลำดับเดียวกัน: derive `Debug`, implement `Display`, *แล้วค่อย* implement `Error` — คอมไพเลอร์ไม่ยอมให้คุณข้ามขั้นตอนไปได้

## Implement `std::error::Error`

เพื่อให้ใช้ได้ทุกที่ที่ต้องการ `dyn Error` (เช่น ใน `Box<dyn Error>`) ประเภทของคุณต้อง implement `std::error::Error` นอกเหนือจาก bound `Debug`/`Display` แล้ว trait นี้ไม่มี method ที่*บังคับ* — default implementation เพียงพอสำหรับกรณีส่วนใหญ่ ถ้าต้องการให้ implement `source()` เพื่อเปิดเผยสาเหตุที่แท้จริง:

```rust
use std::fmt;

#[derive(Debug)]
enum AppError {
    ParseError(std::num::ParseIntError),
    NegativeNumber(i32),
    TooBig(i32),
}

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            AppError::ParseError(e)     => write!(f, "parse error: {}", e),
            AppError::NegativeNumber(n) => write!(f, "number is negative: {}", n),
            AppError::TooBig(n)         => write!(f, "number is too big: {} (max 100)", n),
        }
    }
}

impl std::error::Error for AppError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            AppError::ParseError(e) => Some(e),
            _ => None,
        }
    }
}
```

### เดินตาม Chain ของ `source()`

`source()` เชื่อม error หนึ่งกับ error ระดับล่างที่เป็นสาเหตุของมัน ทีละชั้น ตัวพิมพ์ทั่วไปเดินตาม chain ทั้งหมดด้วย `while let Some(...)` จากข้อความระดับบนสุดลงไปถึงสาเหตุที่แท้จริง:

```rust
use std::error::Error;
use std::fmt;

#[derive(Debug)]
struct ConfigError {
    source: std::num::ParseIntError,
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "invalid config value")
    }
}
impl Error for ConfigError {
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        Some(&self.source)
    }
}

#[derive(Debug)]
struct StartupError {
    source: ConfigError,
}

impl fmt::Display for StartupError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "server failed to start")
    }
}
impl Error for StartupError {
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        Some(&self.source)
    }
}

fn print_chain(err: &dyn Error) {
    println!("Error: {err}");
    let mut source = err.source();
    while let Some(s) = source {
        println!("Caused by: {s}");
        source = s.source();
    }
}

fn main() {
    let parse_err = "abc".parse::<i32>().unwrap_err();
    let config_err = ConfigError { source: parse_err };
    let startup_err = StartupError { source: config_err };
    print_chain(&startup_err);
}
```

การรันโค้ดนี้พิมพ์ chain ทั้งหมด หนึ่งข้อความ `Display` ต่อหนึ่งชั้น จากความล้มเหลวชั้นนอกสุดไปจนถึง `ParseIntError` ดั้งเดิม:

```text
Error: server failed to start
Caused by: invalid config value
Caused by: invalid digit found in string
```

ถ้าไม่มี `source()` chain นั้นก็ไม่มีอยู่เลย — ผู้เรียก (และเครื่องมืออย่างการจัด format `{:?}` ของ `anyhow` ที่แสดงด้านล่าง) จะเห็นได้แค่ข้อความ `Display` ระดับบนสุดตัวเดียวเท่านั้น

## การแปลงอัตโนมัติด้วย `From`

การ implement `From<SomeOtherError> for AppError` ทำให้ตัวดำเนินการ `?` แปลงให้อัตโนมัติเมื่อเรียกฟังก์ชันที่คืนค่า `SomeOtherError`:

```rust
#[derive(Debug)]
enum AppError {
    ParseError(std::num::ParseIntError),
    NegativeNumber(i32),
    TooBig(i32),
}

impl From<std::num::ParseIntError> for AppError {
    fn from(e: std::num::ParseIntError) -> Self {
        AppError::ParseError(e)
    }
}
```

ตอนนี้ `s.parse::<i32>()?` ในฟังก์ชันที่คืนค่า `Result<_, AppError>` จะห่อ `ParseIntError` เป็น `AppError::ParseError` ให้อัตโนมัติ ดู[บทตัวดำเนินการ ?](/rust/th/error-handling/question-mark/) สำหรับสิ่งที่เกิดขึ้นเป๊ะๆ เมื่อ `From` impl นี้ขาดหายไป

## `Box<dyn Error>` ใน Binary เทียบกับ Enum ที่กำหนดเองใน Library

`Box<dyn Error>` ลบประเภท error ที่เป็นรูปธรรมออก — ประเภทใดก็ตามที่ implement `Error` ใส่เข้าไปในนั้นได้ นั่นเหมาะสมพอดีสำหรับ `fn main` ที่สิ่งเดียวที่สำคัญคือ "โปรแกรมล้มเหลวหรือเปล่า และควรพิมพ์อะไร" แต่มันผิดพอดีสำหรับ API *สาธารณะ* ของ library: ผู้เรียกเสียความสามารถในการ `match` ว่าความล้มเหลวไหนเกิดขึ้น และเหลือแค่ตัวเลือกที่งุ่มง่ามคือ downcast ตอนรันไทม์:

```rust
use std::error::Error;
use std::fmt;

#[derive(Debug)]
struct NotFoundError(String);

impl fmt::Display for NotFoundError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "not found: {}", self.0)
    }
}
impl Error for NotFoundError {}

fn lookup(key: &str) -> Result<i32, Box<dyn Error>> {
    if key == "answer" {
        Ok(42)
    } else {
        Err(Box::new(NotFoundError(key.to_string())))
    }
}

fn main() {
    match lookup("missing") {
        Ok(v) => println!("found: {v}"),
        Err(e) => {
            // Box<dyn Error> erases the concrete type, so a caller who wants to
            // react differently to NotFoundError specifically must downcast at runtime.
            if let Some(not_found) = e.downcast_ref::<NotFoundError>() {
                println!("caller can react specifically: {}", not_found.0);
            } else {
                println!("some other error: {e}");
            }
        }
    }
}
```

`downcast_ref::<T>()` คืนค่า `Some(&T)` ก็ต่อเมื่อประเภทจริงตอนรันไทม์ของ trait object คือ `T` — มันคอมไพล์ผ่านได้ไม่ว่า `T: Error + 'static` จะถูกหรือไม่ก็ตาม ดังนั้นคอมไพเลอร์จับ typo ของประเภทตรงนี้ไม่ได้เหมือนที่มันจับ `match` arm ที่ผิดบน enum จริงได้ นี่คือต้นทุนที่เป็นรูปธรรมของการเลือก `Box<dyn Error>` สำหรับ API ที่ผู้เรียกต้อง branch: ผู้เรียกทุกคนที่สนใจต้อง implement การเช็ครันไทม์ที่เปราะบางแบบเดียวกันนี้ซ้ำ แทนที่จะได้ `match` ที่คอมไพเลอร์เช็คให้

## `#[non_exhaustive]` บน Error Enum

การเพิ่ม variant ใหม่ให้ error enum สาธารณะเป็น breaking change สำหรับ crate downstream: `match` ใดๆ ที่ไม่มีสาขา wildcard จะหยุดคอมไพล์ทันทีที่คุณเพิ่ม variant เพราะมันไม่ exhaustive อีกต่อไป `#[non_exhaustive]` เปลี่ยนค่าเริ่มต้นนั้น — มันบังคับให้ทุก crate *ที่ไม่ใช่ของคุณ* ต้องมีสาขา wildcard เพื่อที่คุณจะเพิ่ม variant ในภายหลังได้โดยไม่ทำให้ build ของพวกเขาพัง:

```rust
#[derive(Debug)]
#[non_exhaustive]
pub enum ApiError {
    NotFound,
    Timeout,
}
```

ภายใน crate ที่กำหนดมันเอง `#[non_exhaustive]` ไม่มีผลอะไรเลย — attribute นี้จำกัดแค่ crate *อื่น* เท่านั้น diagnostic จริงด้านล่างมาจาก scratch workspace สองคร่าง: library crate ชื่อ `apilib` ที่กำหนด `ApiError` ด้วย `#[non_exhaustive]` และ `consumer` crate แยกต่างหากที่ match กับมันโดยไม่มี wildcard:

```rust
// @skip-verify cross-crate demo — needs a separate library crate to observe the effect
use apilib::ApiError;

fn describe(e: &ApiError) -> &'static str {
    match e {
        ApiError::NotFound => "not found",
        ApiError::Timeout => "timed out",
    }
}
```

## `thiserror` และ `anyhow`

การเขียน `Display`, `Error`, และ `From` เองสำหรับ error enum ทุกตัวซ้ำซากพอที่ในโลกจริง crate สองตัวครองพื้นที่นี้: `thiserror` สำหรับ error enum ของ library, `anyhow` สำหรับการจัดการ error ระดับ application ไม่มีตัวไหนมากับ toolchain ของคอร์สนี้ ดังนั้น snippet ด้านล่างเป็น `@skip-verify` — output ถูก quote มาแบบคำต่อคำจาก `cargo build && cargo run` จริงใน scratch project ที่เพิ่ม `thiserror = "2"` และ `anyhow = "1"` ผ่าน `cargo add`

`#[derive(Error)]` ของ `thiserror` สร้าง `Display` และ `Error` impl จาก template ข้อความ `#[error("...")]` และ `#[from]` สร้าง `From` impl ให้ในบรรทัดเดียว:

```rust
// @skip-verify crate: thiserror — output quoted from a real scratch cargo build/run below
use thiserror::Error;

#[derive(Error, Debug)]
enum AppError {
    #[error("invalid number: {0}")]
    Parse(#[from] std::num::ParseIntError),
    #[error("value {0} is out of range (0..=100)")]
    OutOfRange(i32),
}

fn parse_bounded(s: &str) -> Result<i32, AppError> {
    let n: i32 = s.parse()?; // ParseIntError -> AppError::Parse via #[from]
    if n > 100 {
        return Err(AppError::OutOfRange(n));
    }
    Ok(n)
}

fn main() {
    for s in ["42", "abc", "999"] {
        match parse_bounded(s) {
            Ok(n) => println!("{s} -> Ok({n})"),
            Err(e) => println!("{s} -> Err: {e}"),
        }
    }
}
```

```text
$ cargo add thiserror && cargo build --quiet && cargo run --quiet
42 -> Ok(42)
abc -> Err: invalid number: invalid digit found in string
999 -> Err: value 999 is out of range (0..=100)
```

`anyhow::Result<T>` (alias ของ `Result<T, anyhow::Error>`) คือคู่หูฝั่ง application: มันคล้าย `Box<dyn Error>` ตรงที่ลบประเภทที่เป็นรูปธรรมออก แต่เพิ่ม `.context(...)`/`.with_context(...)` เพื่อแนบ breadcrumb ที่มนุษย์อ่านได้ในทุกชั้น และการจัด format `{:?}` (`Debug`) ของมันพิมพ์ chain `source()` ทั้งหมดให้คุณโดยอัตโนมัติ:

```rust
// @skip-verify crate: anyhow — output quoted from a real scratch cargo build/run below
use anyhow::{Context, Result};

fn read_port(s: &str) -> Result<u16> {
    s.parse::<u16>()
        .with_context(|| format!("failed to parse '{s}' as a port number"))
}

fn load_config() -> Result<u16> {
    read_port("not_a_port").context("loading server config")
}

fn main() -> Result<()> {
    let port = load_config()?;
    println!("port = {port}");
    Ok(())
}
```

```text
$ cargo add anyhow && cargo build --quiet && cargo run --quiet; echo "exit=$?"
Error: loading server config

Caused by:
    0: failed to parse 'not_a_port' as a port number
    1: invalid digit found in string
exit=1
```

บล็อก `Caused by:` นั้นคือ chain `source()` จากก่อนหน้านี้เป๊ะๆ ที่พิมพ์ให้คุณ — `anyhow` โดยพื้นฐานคือ "ให้ตัวพิมพ์ chain `source()` และกลไกการแปลง `From` แบบฟรีๆ แลกกับการลบประเภท error ที่เป็นรูปธรรม" ซึ่งเป็นเหตุผลว่าทำไมมันเหมาะกับ application (ที่ไม่มีใคร downstream ต้อง `match` กับ error ของคุณ) ไม่ใช่ public API ของ library

<Callout title="เลือกกลยุทธ์ error เดียวต่อขอบเขตของ crate">
การแบ่งที่พบทั่วไปและได้ผล: library crate export enum `thiserror` ที่เป็นรูปธรรมเพื่อให้ผู้เรียก `match` ได้; binary ที่ประกอบ library เหล่านั้นเข้าด้วยกันใช้ `anyhow` ใน `main` และที่ขอบเขตภายในของตัวเอง ที่การลบประเภทและได้ chain `Caused by:` ที่อ่านง่ายคือสิ่งที่คุณต้องการพอดี
</Callout>

## `panic = "abort"` และ `catch_unwind` โดยย่อ

Custom error type มีไว้สำหรับความล้มเหลวที่*กู้คืนได้* — แต่ไม่ใช่ทุกความล้มเหลวจะกู้คืนได้ และ[บท Panics](/rust/th/error-handling/panic/) ครอบคลุมอีกครึ่งหนึ่งของเรื่องนี้อย่างลึกซึ้ง: การตั้ง `panic = "abort"` ใน `Cargo.toml` แลก cleanup แบบ `Drop` กับ binary ที่เล็กลง และ `std::panic::catch_unwind` สามารถแยก panic ที่ขอบเขต FFI หรือ worker thread ได้โดยไม่ทำให้ Rust กลายเป็นภาษาที่มี exception handling ทั่วไป ถ้า custom error enum ของคุณกำลังจะโต variant รูปร่าง `Panic` "เผื่อไว้กรณี callback panic" บทนั้นที่มีเรื่อง `catch_unwind` คือเครื่องมือสำหรับงานนั้น ไม่ใช่ `Err` variant อีกตัว

## แบบจำลองความคิด

คิดถึงรูปร่างของ error type ของคุณว่าเป็นคำสัญญาต่อผู้ฟังสองกลุ่มพร้อมกัน `Debug` และ `Display` มีไว้สำหรับ*มนุษย์* — บรรทัด log, terminal, bug report `Error` (โดยเฉพาะ `source()`) มีไว้สำหรับ*เครื่องมือ* — อะไรก็ตามที่ต้องการเดินตาม failure chain แบบเป็นโปรแกรม เหมือนที่ `{:?}` ของ `anyhow` ทำให้อัตโนมัติ `From` มีไว้สำหรับ*โค้ดของคุณเอง* — กลไกที่ทำให้ `?` ข้ามขอบเขตระหว่าง error type สองตัวได้โดยไม่ต้องเขียน `match` ด้วยมือที่ทุกจุดเรียก error type ที่ออกแบบดีตอบสนองผู้ฟังทั้งสามกลุ่มโดยไม่บังคับให้ใครต้องเดา

## ข้อแลกเปลี่ยน

Enum ที่เป็นรูปธรรมให้ผู้เรียก `match` ที่คอมไพเลอร์เช็คให้และบันทึกทุกโหมดความล้มเหลวไว้ที่เดียว โดยแลกกับการเขียน (หรือ derive) `Display`/`Error`/`From` ให้มันและอัปเดต call site เมื่อคุณเพิ่ม variant — เว้นแต่คุณเพิ่ม `#[non_exhaustive]` ซึ่งจะบังคับให้ผู้เรียกภายนอกทุกคนต้องเขียนสาขา wildcard ตลอดไป `Box<dyn Error>` ไม่ต้องมี boilerplate นั้นเลยและเป็นค่าเริ่มต้นที่ถูกต้องสำหรับ `main` และที่อื่นๆ ที่ไม่มีอะไร downstream ต้อง branch แต่มันผลักผู้เรียกที่*ต้อง* branch จริงๆ ไปสู่การเรียก `downcast_ref` ตอนรันไทม์ที่คอมไพเลอร์เช็คไม่ได้ `thiserror` และ `anyhow` ลบ boilerplate ที่เหลือส่วนใหญ่ในแต่ละฝั่งของเส้นนั้น โดยแลกกับ dependency และสำหรับ `anyhow` คือข้อแลกเปลี่ยนการลบประเภทแบบเดียวกับ `Box<dyn Error>`

## ความเข้าใจผิดที่พบบ่อย

- **"`Box<dyn Error>` ใช้ได้เสมอเพราะคุณ `downcast_ref` ได้ถ้าต้องการประเภทที่เป็นรูปธรรมจริงๆ"** คุณทำได้ แต่คอมไพเลอร์เช็คไม่ได้ว่า `downcast_ref::<T>()` ที่คุณเขียนคือประเภทที่ถูก return จริงๆ — typo หรือการ refactor เปลี่ยนมันจาก "สาขานี้รัน" เป็น "สาขานี้ไม่เคยรัน" แบบเงียบๆ โดยไม่มี error เลย
- **"`#[non_exhaustive]` ทำให้ enum กันการ exhaustive ได้ทุกที่ รวมถึง crate ของฉันเอง"** มันไม่มีผลอะไรเลยภายใน crate ที่กำหนดมัน — คุณยัง match โดยไม่มี wildcard ที่นั่นได้อยู่ มันเปลี่ยนแค่สิ่งที่ crate *อื่น* ถูกบังคับให้เขียน
- **"`anyhow` และ `thiserror` ทำงานเดียวกัน ฉันต้องการแค่ตัวเดียว"** พวกมันแก้ปัญหาคนละครึ่ง: `thiserror` สร้างประเภทที่เป็นรูปธรรม match ได้ (สำหรับ library); `anyhow` สร้างประเภทที่ถูกลบไปพร้อมคำอธิบายบริบทและการจัด format chain อัตโนมัติ (สำหรับ application) การใช้ `anyhow::Error` เป็น return type สาธารณะของ library นำปัญหา downcasting แบบเดียวกับ `Box<dyn Error>` กลับมาให้ผู้เรียกของมัน
