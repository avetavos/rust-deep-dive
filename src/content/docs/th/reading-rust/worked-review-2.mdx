รีวิวเต็มบทที่สอง: โปรแกรมติดตาม inventory เล็ก ๆ ที่สร้างรอบ struct กับ enum กระบวนการเดียวกับก่อนหน้า — อ่านมันก่อน สร้างความเห็นของตัวเอง แล้วเทียบกับ findings ด้านล่าง

## โปรแกรม

export const wr2BuggyCode = `#[derive(Clone, Copy)]
struct Item {
    id: u32,
    price: f64,
    stock: u32,
    barcode: [u8; 64],
}

enum Status {
    InStock,
    LowStock,
    OutOfStock,
    Discontinued,
}

fn status_label(status: Status) -> &'static str {
    match status {
        Status::InStock => "in stock",
        _ => "unavailable",
    }
}

fn find_item_by_price(items: &[Item], target_price: f64) -> Option<&Item> {
    items.iter().find(|item| item.price == target_price)
}

fn total_value(items: &[Item]) -> f64 {
    items.iter().map(|i| i.price * i.stock as f64).sum()
}

fn describe_cheapest(items: &[Item]) -> String {
    let cheapest = items.iter().min_by(|a, b| a.price.partial_cmp(&b.price).unwrap());
    if cheapest.is_some() {
        format!("cheapest item id: {}", cheapest.unwrap().id)
    } else {
        "no items".to_string()
    }
}

fn apply_discount(item: Item, percent: f64) -> Item {
    let mut discounted = item;
    discounted.price *= 1.0 - percent / 100.0;
    discounted
}

fn main() {
    let items = vec![
        Item { id: 1, price: 9.99, stock: 10, barcode: [0; 64] },
        Item { id: 2, price: 24.50, stock: 3, barcode: [0; 64] },
        Item { id: 3, price: 4.25, stock: 0, barcode: [0; 64] },
    ];

    println!("{}", status_label(Status::InStock));
    println!("{}", status_label(Status::LowStock));
    println!("{}", status_label(Status::OutOfStock));
    println!("{}", status_label(Status::Discontinued));

    if let Some(found) = find_item_by_price(&items, 9.99) {
        println!("found item {} at $9.99", found.id);
    }

    println!("total value: \${:.2}", total_value(&items));
    println!("{}", describe_cheapest(&items));

    let discounted = apply_discount(items[1], 10.0);
    println!("discounted price: \${:.2}", discounted.price);
    println!("original still: \${:.2}", items[1].price);
    println!("size of Item: {} bytes", std::mem::size_of::<Item>());
}`;

## Findings

<details>
<summary>Bug 1: `_ =>` รวมสถานะต่างกันสามแบบให้เหลือแบบเดียว</summary>

**อาการ:** `LowStock`, `OutOfStock`, และ `Discontinued` ทั้งหมด print `"unavailable"` — มองเห็นได้ตรงนี้ใน output แต่อ่านผ่านง่ายว่าเป็น "fallback branch ทำงานตามที่ตั้งใจ" แทนที่จะเป็น "สามสถานะจริงที่ไม่มี label แยกกัน"

**หลักฐาน:**

```text
warning: wildcard match will also match any future added variants
  --> src/main.rs:19:9
   |
19 |         _ => "unavailable",
   |         ^ help: try: `Status::LowStock | Status::OutOfStock | Status::Discontinued`
```

(`cargo clippy -- -W clippy::wildcard_enum_match_arm`)

**ทางแก้:** list ทุก variant อย่างชัดเจน — compiler จะรับประกันว่า `Status` variant ที่ห้าในอนาคตจะ compile ไม่ผ่านตรงนี้จนกว่ามันจะได้ label ของตัวเอง แทนที่จะเข้าไปรวมกับ bucket "unavailable" อย่างเงียบ ๆ:

```rust
// @skip-verify fragment: Status is defined earlier in the full listing above
fn status_label(status: Status) -> &'static str {
    match status {
        Status::InStock => "in stock",
        Status::LowStock => "low stock",
        Status::OutOfStock => "out of stock",
        Status::Discontinued => "discontinued",
    }
}
```
</details>

<details>
<summary>Bug 2: `find_item_by_price` เปรียบเทียบ float ด้วย `==`</summary>

**อาการ:** ไม่มีเลยใน run นี้ — `9.99` ใน search call และ `9.99` ใน price field ของ item เป็น literal เดียวกัน encode เหมือนกัน ดังนั้น `==` จึงบังเอิญสำเร็จ มันหยุดสำเร็จทันทีที่ฝั่งใดฝั่งหนึ่งเป็นผลจากการคำนวณ (ส่วนลด, การแปลงสกุลเงิน, ผลรวม) แทนที่จะเป็น literal ที่ตรงกัน

**หลักฐาน:**

```text
warning: strict comparison of `f32` or `f64`
  --> src/main.rs:24:30
   |
24 |     items.iter().find(|item| item.price == target_price)
   |                              ^^^^^^^^^^^^^^^^^^^^^^^^^^ help: consider comparing them within some margin of error: `(item.price - target_price).abs() < error_margin`
```

(`cargo clippy -- -W clippy::float_cmp`)

**ทางแก้:** เปรียบเทียบภายใน tolerance แทนที่จะเป็นความเท่ากันแบบเป๊ะ:

```rust
// @skip-verify fragment: Item is defined earlier in the full listing above
fn find_item_by_price(items: &[Item], target_price: f64) -> Option<&Item> {
    items.iter().find(|item| (item.price - target_price).abs() < f64::EPSILON)
}
```

ทางแก้ที่ทนทานกว่าในโลกจริงคือเก็บราคาเป็นจำนวนเต็มหน่วยเซนต์ (`u32`) แทนที่จะเป็น `f64` เลย ซึ่งหลีกเลี่ยงการเปรียบเทียบ float ไปทั้งหมด — คุ้มที่จะพิจารณาตรงนี้ แต่อยู่นอกขอบเขตของ fix เฉพาะนี้
</details>

<details>
<summary>Bug 3: `is_some()` แล้ว `unwrap()` ใน `describe_cheapest`</summary>

**อาการ:** ไม่มี — ถูกต้องทาง logic แค่ทำด้วยมือในสิ่งที่ `match`/`if let` ทำในขั้นตอนเดียวอยู่แล้ว และเลยเป็นแค่การแก้ไขหนึ่งครั้งห่างจาก bug (ไม่มีอะไรหยุด edit ในอนาคตจากการเปลี่ยนสิ่งที่ `cheapest` ถืออยู่ระหว่างการเช็ค `is_some()` กับการเรียก `unwrap()`)

**หลักฐาน:**

</details>

<details>
<summary>Bug 4: `#[derive(Copy)]` บน struct 80 ไบต์</summary>

**อาการ:** `apply_discount(items[1], 10.0)` compile ผ่านและทำงานถูกต้อง — แต่ `items[1]` ถูกส่งแบบ*by value* และเพราะ `Item` เป็น `Copy` โค้ดนี้จึง copy ทั้ง 80 ไบต์อย่างเงียบ ๆ แทนที่จะ move หรือ borrow `items[1]` ยังใช้ได้สมบูรณ์ในบรรทัดถัดไป (`original still: $24.50`) เพราะไม่มีอะไรถูก move เลยพอดี — มีแค่ copy ธรรมดาเกิดขึ้นแบบมองไม่เห็น

**หลักฐาน:** ไม่มี lint ตัวไหน flag สิ่งนี้เลย — มีแค่การวัดเท่านั้นที่เผยมัน:

```text
size of Item: 80 bytes
```

`#[derive(Copy)]` ถูกกฎตรงนี้ (ทุก field เป็น `Copy`-eligible... ยกเว้น `barcode: [u8; 64]` ซึ่งก็เป็น `Copy` เหมือนกัน เพราะ array ของ type ที่ `Copy` ก็ `Copy`) — ความถูกกฎไม่เคยเป็นประเด็นเลย มีแค่ว่าการ copy 80 ไบต์ทุกครั้งที่ใช้แบบ by-value เป็นต้นทุนที่ตั้งใจหรือไม่

**ทางแก้:** ตัด `Copy` ออก (เก็บ `Clone` ไว้) และรับ `&Item` แบบ reference ในที่ที่ฟังก์ชันแค่ต้องการอ่านมัน clone แค่ในที่ที่ต้องการ copy แบบ mutable ที่เป็นอิสระจริง ๆ:

```rust
// @skip-verify fragment: Item is defined earlier in the full listing above
fn apply_discount(item: &Item, percent: f64) -> Item {
    let mut discounted = item.clone();
    discounted.price *= 1.0 - percent / 100.0;
    discounted
}
// call site: apply_discount(&items[1], 10.0)
```

การแก้นี้ทำให้ clone ชัดเจนและมองเห็นได้ที่ call site เดียวที่ต้องการ copy ที่เป็นอิสระจริง ๆ แทนที่จะปล่อยให้การใช้ `Item` แบบ by-value ในอนาคตทุกครั้ง copy 80 ไบต์อย่างเงียบ ๆ
</details>

## Mental Model

Struct กับ enum encode รูปร่างครั้งเดียวแล้วถูก copy, match, และเปรียบเทียบทุกที่ที่ type นั้นถูกใช้ — ซึ่งหมายความว่าความผิดพลาดด้าน design ที่จุดนิยาม type (การ derive `Copy` บนสิ่งที่ใหญ่, การปล่อยให้ status ไม่มี label ครบทุก variant) ไม่ได้อยู่แค่ที่เดียว มันโผล่กลับมาที่ทุก call site ที่รับ struct แบบ by value และทุก `match` ที่หยิบ `_` แทนที่จะ list variant การรีวิว struct หรือ enum definition คุ้มค่าความสนใจเท่ากับการรีวิว public function signature ด้วยเหตุผลเดียวกัน: ทุกอย่างที่อยู่ปลายน้ำสืบทอดการตัดสินใจที่ทำไว้ตรงนั้น

## Trade-offs

การ list ทุก enum variant อย่างชัดเจน (แก้ Bug 1) เสียบรรทัดเพิ่มขึ้นสองสามบรรทัดวันนี้ และคุ้มค่าทันทีที่ `Status` variant ที่ห้าถูกเพิ่มเข้ามา — compiler บังคับให้ทุก `match` ที่ได้รับผลกระทบถูกอัปเดต แทนที่จะปล่อยให้มันตกลงไปที่ `_` อย่างเงียบ ๆ นั่นเป็นการแลกจริง ที่ตั้งใจ: verbose มากขึ้นตอนนี้ ปลอดภัยมากขึ้นเมื่อมีการเปลี่ยนแปลงทีหลัง การ redesign float-to-cents ที่กล่าวถึงใน fix ของ Bug 2 เป็นเวอร์ชันที่ทั่วถึงกว่าของการแลกเปลี่ยนแบบเดียวกัน — `u32` เซนต์เสียค่า refactor ครั้งเดียวและลบ bug ประเภทเปรียบเทียบ float ทั้งหมดออกไปถาวร แทนที่จะปะ call site เดียวด้วยการเปรียบเทียบ epsilon

## Common Misconceptions

- **"`_ =>` เป็นแค่เวอร์ชัน Rust ของ `default`/`else` -- ใช้มันได้เสมอโดยไม่มีปัญหา"** มัน compile เป็นแบบนั้นจริง แต่มันยัง opt-out จาก exhaustiveness checking ของ `match` เฉพาะตัวนั้น ซึ่งเป็นเหตุผลหลักที่ใช้ `match` แทน `if`/`else` chain ตั้งแต่แรก การแลกเปลี่ยนนี้ชอบธรรมสำหรับบาง match (ชุด case ที่เปิดกว้างจริง) และเป็นความเสี่ยงจริงสำหรับ match อื่น (enum เล็ก ๆ ปิดตัวอย่าง `Status`)
- **"`#[derive(Copy)]` เกี่ยวกับ performance เท่านั้น ไม่เกี่ยวกับความถูกต้อง"** ในตัวอย่างนี้มันเกี่ยวทั้งคู่: การ copy 80 ไบต์อย่างเงียบ ๆ เป็นต้นทุนด้าน performance และความจริงที่ว่า `items[1]` ยังใช้ได้หลัง `apply_discount(items[1], ...)` — เพราะมันถูก copy ไม่ใช่ move — ก็สามารถกลบ bug ที่ผู้เรียก*ตั้งใจ*จะกิน original แต่บังเอิญยังมีมันอยู่ได้ด้วย

## อ่านโค้ดที่ AI เขียน

รูปร่างเดียวกันของ `_ =>` โผล่มาบ่อยมากใน match statement ที่ AI สร้างบน enum เล็ก ๆ ปิด มักเพราะผู้เขียน (มนุษย์หรือ AI) กำลังคิดถึงกรณี*ที่พบบ่อย* ไม่ใช่กรณี*ที่ครบถ้วน*

</SpotTheBug>
