## Static vs Dynamic Dispatch

Rust มีสองวิธีในการใช้ trait polymorphism:

- **Static dispatch** (ผ่าน generics): compiler รู้ exact type ณ compile time และสร้าง code เฉพาะสำหรับแต่ละ type ไม่มี runtime overhead
- **Dynamic dispatch** (ผ่าน `dyn Trait`): concrete type ไม่ทราบจนกว่าจะถึง runtime compiler จะเก็บ *vtable* — ตารางของ function pointer — คู่กับค่านั้น เพื่อให้หา method ที่ถูกต้องได้ ณ runtime

## Syntax `dyn Trait`

เมื่อคุณเขียน `dyn Animal` คุณกำลังขอให้ Rust ใช้ dynamic dispatch เนื่องจาก size ของ concrete type ไม่ทราบ ณ compile time คุณต้องวาง `dyn Trait` ไว้หลัง pointer รูปแบบที่พบบ่อยที่สุดสองแบบคือ:

- `&dyn Trait` — trait object แบบ borrowed (ไม่ allocate heap)
- `Box<dyn Trait>` — trait object แบบ owned ที่เก็บบน heap

```rust
trait Animal {
    fn sound(&self) -> &str;
    fn name(&self) -> &str;
}

fn make_sound(animal: &dyn Animal) {
    println!("{} says: {}", animal.name(), animal.sound());
}
```

ฟังก์ชันนี้รับ type *ใดก็ได้* ที่ implement `Animal` — คุณไม่จำเป็นต้องรู้ concrete type ณ compile time

## เก็บหลาย Type ใน Collection เดียว

การใช้งานที่ทรงพลังที่สุดของ trait object คือการเก็บค่าที่มี concrete type ต่างกันไว้ใน `Vec` หรือ collection อื่นร่วมกัน ถ้าใช้ generics เพียงอย่างเดียวจะทำแบบนี้ไม่ได้ — `Vec<T>` เก็บได้แค่ concrete type เดียวในแต่ละครั้ง

```rust
trait Animal {
    fn sound(&self) -> &str;
    fn name(&self) -> &str;
}
struct Dog;
struct Cat;
impl Animal for Dog {
    fn sound(&self) -> &str { "Woof" }
    fn name(&self) -> &str { "Dog" }
}
impl Animal for Cat {
    fn sound(&self) -> &str { "Meow" }
    fn name(&self) -> &str { "Cat" }
}

let animals: Vec<Box<dyn Animal>> = vec![
    Box::new(Dog),
    Box::new(Cat),
    Box::new(Dog),
];
```

แต่ละ element เป็น `Box<dyn Animal>` — pointer แบบ owned ไปยัง type ใดก็ตามที่ implement `Animal` vtable ที่เก็บคู่กับแต่ละค่ารับประกันว่า `sound()` และ `name()` ที่ถูกต้องจะถูกเรียก

## `impl Trait` vs `dyn Trait`

ทั้ง `&impl Animal` และ `&dyn Animal` รับ "type ใดก็ได้ที่ implement `Animal`" เป็น parameter ของฟังก์ชัน แต่ compile ออกมาต่างกันมาก:

```rust
trait Animal {
    fn sound(&self) -> &str;
}
struct Dog;
impl Animal for Dog { fn sound(&self) -> &str { "Woof" } }

// Static dispatch -- compiler generates specialized code per concrete type
fn notify_static(item: &impl Animal) {
    println!("{}", item.sound());
}

// Dynamic dispatch -- resolved at runtime via vtable
fn notify_dyn(item: &dyn Animal) {
    println!("{}", item.sound());
}

fn main() {
    notify_static(&Dog);
    notify_dyn(&Dog);
}
```

`&impl Animal` เป็น shorthand ของ generic type parameter (`fn notify_static<T: Animal>(item: &T)`) — compiler จะ monomorphize มันเหมือนกับ generics ที่คุณเห็นในบทก่อนหน้า ส่วน `&dyn Animal` คือ trait object — ฟังก์ชันเดียว ที่ dispatch ผ่าน vtable ณ runtime ใช้ `impl Trait` เมื่อรู้ type ณ compile time และต้องการประสิทธิภาพสูงสุด ใช้ `dyn Trait` เมื่อต้องการความยืดหยุ่น ณ runtime เช่นเก็บหลาย type ใน `Vec` หรือ return type ต่างกันจากแต่ละ branch

## Trait Objects และ Dyn Compatibility

ไม่ใช่ทุก trait จะใช้เป็น `dyn Trait` ได้ trait จะ **dyn compatible** ถ้าโดยคร่าวๆ:

1. ไม่มี method ที่ return `Self`
2. ไม่มี generic type parameter บน method ของมัน

(เอกสารเก่า — รวมถึงประวัติศาสตร์ของ Rust เอง — เรียกสิ่งนี้ว่า *object safety*; rustc ปัจจุบันใช้คำว่า *dyn compatible* / *dyn compatibility* ใน diagnostic ดังนั้นบทนี้จึงใช้คำนี้)

trait มาตรฐานอย่าง `Display`, `Debug` และ `Iterator` เป็น dyn compatible ส่วน trait อย่าง `Clone` (ที่ method `clone` return `Self`) ไม่ใช่ — การใช้มันเป็น `&dyn Trait` คือ compile error:

```rust
// @expect-error E0038
trait Animal {
    fn sound(&self) -> &str;
    fn clone_animal(&self) -> Self; // returns Self -- not dyn compatible
}

struct Dog;

impl Animal for Dog {
    fn sound(&self) -> &str { "Woof" }
    fn clone_animal(&self) -> Self { Dog }
}

fn make_sound(animal: &dyn Animal) {
    println!("{}", animal.sound());
}

fn main() {
    make_sound(&Dog);
}
```

```text
error[E0038]: the trait `Animal` is not dyn compatible

   |                        ^^^^^^^^^^ `Animal` is not dyn compatible
```

สังเกตคำที่ใช้: rustc พูดว่า "is not dyn compatible" — ไม่มีคำว่า "object safety" หรือ "object-safe" ปรากฏใน diagnostic เลย

### ทางออก `where Self: Sized`

คุณไม่จำเป็นต้องเลิกใช้ trait ทั้งตัวเพียงเพราะ method เดียวไม่ dyn compatible การเพิ่ม bound `where Self: Sized` ให้ method นั้นจะเอามันออกจากข้อกำหนดของ vtable — method จะใช้ผ่าน `dyn Trait` ไม่ได้ แต่ trait เองกลับมา dyn compatible อีกครั้ง และ method ยังใช้งานได้เมื่อเรียกบน concrete type ที่รู้แน่ชัด ณ compile time:

```rust
trait Animal {
    fn sound(&self) -> &str;
    fn clone_animal(&self) -> Self
    where
        Self: Sized; // excluded from the vtable -- only callable when Self is statically known
}

struct Dog;

impl Animal for Dog {
    fn sound(&self) -> &str { "Woof" }
    fn clone_animal(&self) -> Self { Dog }
}

fn make_sound(animal: &dyn Animal) {
    println!("{}", animal.sound());
}

fn main() {
    make_sound(&Dog);            // fine: dyn dispatch only needs sound()
    let d2 = Dog.clone_animal(); // fine: called on the concrete type, not through dyn
    make_sound(&d2);
}
```

## เมื่อใดควรใช้แบบไหน

| แนวทาง | รู้ type ณ compile time? | Runtime cost | เก็บหลาย type ใน collection เดียวได้? |
|---|---|---|---|
| Generic (`impl Trait` หรือ `T: Trait`) | ใช่ | ไม่มี | ไม่ได้ |
| Trait object (`dyn Trait`) | ไม่ | vtable indirection เล็กน้อย | ได้ |

ใช้ generics เมื่อรู้ type ณ compile time และต้องการประสิทธิภาพสูงสุด ใช้ trait object เมื่อต้องทำงานกับ collection ที่มี concrete type ปนกัน หรือเมื่อ type ถูกกำหนด ณ runtime จาก input หรือ configuration ของผู้ใช้

export const traitObjectsCode = `trait Animal {

    fn name(&self) -> &str { "Dog" }
}

impl Animal for Cat {
    fn sound(&self) -> &str { "Meow" }
    fn name(&self) -> &str { "Cat" }
}

fn make_sound(animal: &dyn Animal) {
    println!("{} says: {}", animal.name(), animal.sound());
}

fn main() {
    let animals: Vec<Box<dyn Animal>> = vec![
        Box::new(Dog),
        Box::new(Cat),
        Box::new(Dog),
    ];

    for animal in &animals {
        make_sound(animal.as_ref());
    }
}`;
